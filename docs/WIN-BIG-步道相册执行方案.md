# WIN BIG · 步道相册执行方案

状态：第一版连续步道已完成。开场 Logo 居中；六站各带不同的济州风味装饰、韩语路牌、花字标题与中文“留句话”入口；每站下方以卡片+阴影空间感完整展示来自《2026H2济州岛团建活动反馈收集》的全部 8 位同事反馈；完整相册与本地留言保留。多人留言后端和正式内部部署仍未执行。

## 一、设计目标

从“单张照片轮播 + 文字过渡”改为一条可前进、可停留、可回头的记忆步道。

核心构图：**道路中间是 WIN BIG，两边各两张照片，上下排列。**

```text
                    道路通往远处
                         ↑
        ┌─────────┐           ┌─────────┐
        │ 左侧上图 │           │ 右侧上图 │
        └─────────┘   WIN     └─────────┘
                      BIG
        ┌─────────┐           ┌─────────┐
        │ 左侧下图 │           │ 右侧下图 │
        └─────────┘           └─────────┘
                    观看者所在位置
```

这是构图示意，不是四宫格页面：道路向远方收窄，照片有真实远近关系，后方下一组展位在远处可见。

### 空间规则

- 道路：浅色、低细节的展览步道，不做沥青马路、交通标线或游戏赛道。
- WIN BIG：先做成道路中央略有厚度的字标；属于场景，会随前进靠近并经过，不固定在屏幕上挡住照片。开场完整呈现，后续仅在活动入口少量出现，不每四张机械重复。
- 照片：每侧上下两张，偏向观看者、只轻微向道路内侧转动。不能为了“立体”侧转到人物和内容看不清。
- 景深：当前四张清楚、下一组在远处较小。前进时照片变大并向两侧离开视野，不是先消失再切下一组。
- 保持稳定视线，不加入自动旋转、镜头摇晃或强烈模糊。立体感来自共同透视、遮挡、距离和接地阴影。
- Lato、中文无衬线回退、原 Logo、浅色自然配色继续保留。
- 不恢复活动编号、照片编号、文件名、操作说明、数字导航、假游戏积分或任务。

### 内容规则

- 多张同屏是本次的新方向，替代原先“一次一张”的主浏览限制；单张仍可点开细看。
- 每个活动按现有照片顺序每四张分组，约定阅读顺序为左上、右上、左下、右下。
- 不跨活动凑数；不足四张保留空位与留白，不复制照片填满。
- 不将上下排当作不同日期。活动顺序是文档分区顺序，不声称已核验完整时间线。
- 当前 183 张图片，119 张横向、64 张竖向，含一张超宽拼图。保持原始比例，展位内留白，必要时调整照片框尺寸；大图阅读默认完整显示。
- 不动原始照片；文案、引文来源与新增留言明确区分，不把引用伪装成网站上的用户留言。

## 二、交互流程

### 1. 进入

打开即可看到道路、中央 WIN BIG 和第一组两侧照片，不再先看大段玩法说明或独立 Logo 等待页。品牌 Logo 留在页面角落，活动标题在入口附近出现。

### 2. 沿路前进

- 纵向滚动是唯一主行进方向；鼠标滚轮、触控板、手机上下滑动使用同一进度来源。
- 不设置自动行走，不劫持全页滚轮，不再要求横向划完几十张才能继续。
- 四张照片同时接近和经过，每组有足够的可阅读距离；同活动内仅自然经过，不触发大型门框动画。
- 反向滚动原路返回，照片仍在原来的空间位置。
- 不强制用户看完每组；若完整步道试走过长，可加入收起的活动名称目录或普通相册入口，而非恢复一排数字。

### 3. 停下来细看

- 照片本身是点击/键盘可聚焦的入口，不额外覆盖玩法文字。
- 点击后进入平面的高清阅读层，不让文字和照片细节一直处于倾斜状态。
- 进入阅读层时锁定步道当前位置，滚动只影响阅读层；关闭或按 Esc 后回到同一位置、同一焦点。
- 防止滑动结束误触；不关闭浏览器缩放和正常手机手势。

### 4. 活动交界

活动之间依靠道路留白、路旁活动名称和下一组照片的接近完成过渡。无需“穿过某某、去往某某”的整屏大字，也不在每一站重复造门、传送或失去方位。

### 5. 留言

- 每个活动保留一个留言入口，建议设置在该活动的路旁停留区。
- 一条精选反馈可以作为旁边的纸笺，但不遮挡照片、不满屏漂浮。
- 留言阅读和输入使用稳定的二维面板，避免打字时路面仍在移动。
- 保留现有本机留言及活动归属，不因换场景重置数据。
- 共享留言及 Feishu 登录是独立的上线工作，不与空间原型绑在一起。接入前明确标注仅本机保存。

### 6. 移动端及减少动态效果

- 平板、大屏优先完整的左右各两张构图。
- 手机先验证缩窄道路后的四张构图；如果照片小到看不清，改为左右交错的双列排布，上下两层展开，而非强行缩成四个小图标。
- “减少动态效果”使用真实的文档流照片布局，不只是给 3D 元素统一设置 transform:none。
- 横屏短视口、手机地址栏高度变化、窗口缩放都不能造成活动不可达或阅读位置跳变。

## 三、当前版本架构检查

检查文件：`index.html`、`styles.css`、`script.js`、`activity-data.js`、`README.md`；另检查了现有临时浏览器测试，并对本地预览做了定点验证。

### 可复用

- 11 个活动的稳定 id、183 张图片清单、现有顺序。
- 品牌资源、Lato 字体文件、色彩体系。
- 原生 dialog 留言面板、输入验证、用 textContent 渲染用户内容的安全方式。
- 本机留言存储键 `jinqiu.jeju.activity-comments.v1` 与 activityId 关联。
- requestAnimationFrame 合并滚动更新的基本方式。

### 必须改变

| 问题 | 当前依据 | 优化方案 |
| --- | --- | --- |
| 不是连续空间 | `index.html` 分为 launch、activity-panel、activity-transition；各自切换显示 | 建立共同道路、世界坐标和镜头进度，阅读面板独立于场景 |
| 照片退场动效不可见 | `script.js:283–302`：inTransition 时 activityOpacity 为 0，同时才设置向后位移；浏览器验证 opacity=0 | 在可见空间中接近、经过、离开视野；透明度只用于远处轻淡出 |
| 3D 上下文分散 | `styles.css` 的 stage 与 gallery 各有 perspective，且混用滚动容器、透明度和 preserve-3d | 单一透视视口 + 独立世界容器；避免在需保留 3D 的祖先上用会压平子层的分组效果，淡出应用于叶节点 |
| 返回活动丢位置 | `renderActivity()` 每次 replaceChildren；实测活动返回后 scrollLeft 从 2107 变为 0 | 以稳定的路程位置与 photoId 为状态源，渲染销毁不影响位置 |
| 短屏走不完整条路 | 轨道长度用 svh，行进距离却除以 stage.clientHeight；844×390 时 stage=620，最大只到约 9.06 个单位，末尾仍停在花园迷宫 | 从同一条路线模型计算总距离与滚动范围，统一测量，视口改变时按语义位置恢复 |
| 减少动态效果有定位错误 | `styles.css:188` 清除了开场居中的 transform；实测开场左上角到了屏幕中心 | 单独的平面渲染模式，布局不依赖运动变换 |
| 帧内工作过多 | updateGalleryDepth 在滚动时遍历全部照片读 offset 再写 transform/shadow；过渡标题每次更新都 replaceChildren | 缓存节点与尺寸，读写分离，只在内容变化时更新 DOM；帧内只更新可见场景的样式 |
| 图片资源偏重 | 183 张直接引用原图，合计约 599.8 MiB，最大单图约 17.4 MiB，尚无这批照片的响应式派生图 | 生成屏幕预览和大图两档资源，显式窗口化加载，而不是仅依赖 loading=lazy |
| 留言与场景耦合 | 一个 script.js 同时处理资源、布局、滚动、留言校验和存储 | 拆分数据、路线、场景、阅读层、留言存储职责 |
| 可访问性需补齐 | activity-panel 的 aria-labelledby 指向不存在的 activity-title；隐藏面板未设置 inert | 正确标题关联、可聚焦照片、非当前场景 inert、原生 dialog 焦点返回与 Esc |
| 测试难复用 | 测试只在 /tmp，依赖机器上的临时 Playwright 路径；多数断言数量/样式字符串而非空间结果 | 项目内测试及固定命令，加入关键帧截图和连续前进/后退的行为断言 |
| 并未真正生产部署 | 本地为 Python 静态服务，无共享后端或身份验证 | 内部托管与访问控制单独落地，只发布构建产物；noindex 不是权限控制 |

备注：599.8 MiB 是全部源文件体积，不代表首屏已下载的体积。若某个完整活动的原图都以 RGBA 解码，理论像素缓冲最高约 1.25 GiB；这不是已测得的浏览器内存值，但说明需要控制加载与解码数量。

## 四、建议技术架构

### 路线选择

第一版采用 **原生 JavaScript 模块 + CSS 3D 的统一场景**。现在的照片、文字、纸笺均是平面内容，先不引入 Three.js、游戏引擎、React 或复杂物理模拟。

可加 Vite 作为轻量开发/构建工具，用于模块组织、依赖锁定和产物隔离；不是为了重写成大型框架。只有原型验证表明确需复杂模型、动态光照或 CSS 无法稳定实现的空间遮挡，才重新评估 WebGL。

### 建议目录与职责

```text
index.html                    页面外壳
src/
  main.js                     初始化与模式选择
  data/
    activities.js             活动文案、photoIds、引文来源
    photos.json               稳定 id、尺寸、比例、派生资源与源文件映射
  route/
    layout.js                 4 张分组、左右/上下槽位、活动边界与空间坐标
    progress.js               滚动位置 -> 路程位置，前进/回退、缩放恢复
  scene/
    renderer.js               道路、字标、照片展位与可见窗口
    motion.js                 唯一镜头变换、各平台动效参数
  ui/
    photo-viewer.js            高清查看、关闭返回、焦点管理
    comments.js                活动留言界面与草稿
  storage/
    comments.js                local 实现与未来共享接口边界
  styles/
    base.css                  字体、颜色、基础规则
    scene.css                 空间布局
    panels.css                查看图/留言层
    fallback.css              小屏与减少动态效果
scripts/
  prepare-images.*            派生图与尺寸清单生成
  validate-data.*             图片存在、分组与覆盖校验
tests/                        数据、交互与视觉回归
docs/                         方案、来源说明与验收记录
```

不将每个图块拆成一套业务逻辑：展位只由数据描述，不为 11 个活动写 11 份动画。

### 关键数据边界

- `Activity`：id、标题、照片 id 列表、反馈来源。
- `Photo`：id、源文件、宽高、预览资源、大图资源。
- `Bay`（展位）：id、activityId、最多四个 photoId、路程坐标、左右/上下槽位。
- `JourneyState`：当前展位、展位内进度、活动 id、打开的照片/留言面板。
- 来源说明、文案与照片清单不保存运行时滚动状态；布局算法也不修改原始活动数据。
- 留言使用稳定 activityId，保留原存储键；必要的格式迁移先备份，不能静默清空现有留言。

### 场景层级

```text
视口裁切层
  统一 perspective
    世界容器（preserve-3d、稳定坐标）
      道路地面
      WIN BIG 字标
      当前/邻近照片展位
      活动名称与路旁纸笺
二维界面层（与世界容器平级）
  品牌、必要入口
  大图 dialog / 留言 dialog
```

所谓镜头，是把整个世界相对于观看者沿深度方向移动；所有物件共用同一进度、同一透视，不各自播放不相关的缩放动画。

### 照片与性能

- 分活动每四张分组，现有数据共 50 组展位。花园迷宫 10 组、撕名牌 9 组，需重点验证长活动节奏。
- 第一版默认完整覆盖 183 张，不在用户未确认时自动改成只展示精选图。
- 道路长度按展位和活动间留白生成，不按“每个活动固定 1.35 屏”。整体长度先通过实走校准，不为了减少滚动而让照片瞬间飞过。
- 默认仅挂载当前及前后邻近展位，例如三组、约 12 张；远处可见预告按需增加，不一次给 183 张都开 GPU 图层。
- 生成 WebP 预览及常用大图，保留原图不改；超宽拼图单独检查分辨率与完整阅读。
- 页面加载图像尺寸已知，避免解码完成后布局跳动；失败时可重试，不把整个活动留空。
- 预览尺寸和压缩率以人物清晰度验收，首屏资源以数 MiB 为初步预算；这些是目标，不是当前达成值。
- 优先更新 transform，不逐帧改变布局或大面积 box-shadow/blur；不可见时暂停更新。

## 五、分阶段执行

### 阶段 0：保护基线和整理素材

- 将当前版本完整快照保留，新版本通过独立预览入口试做，不先覆盖首页。
- 保留原图、活动 id、留言存储与旧版本。
- 建立图片尺寸/资源清单，生成第一批预览图。
- 将测试移入项目，补齐上述短屏、回退、减少动态效果的已知问题用例。

**交付：**可回退的基线、照片清单与可重复测试入口。

### 阶段 1：只做构图样片

- 使用真实素材搭建一组“左二 / 中央 WIN BIG / 右二”。
- 道路在远处可见，下一组照片只做轮廓预告。
- 先不做复杂动画、不接后台，验证横图、竖图和中央字标的比例。
- 同时给出桌面与手机构图，避免桌面定稿后才发现手机放不下。

**验收：**不看任何说明，也能一眼认出“站在路中间看两边照片”；四张照片可辨认，WIN BIG 不压住人物。

### 阶段 2：连续行走样片

- 至少三组展位：同一活动两组（8 张）+ 下一活动一组（4 张），验证组内推进和跨活动不是同一种切屏。
- 实现滚动前进、回退、点击细看、关闭回原处。
- 验证同一批照片在远处、眼前、经过身边时的连续性。
- 删除依赖整屏文字的过渡；保留活动边界的自然留白。
- 接回现有活动留言入口，锁住阅读时的路线进度。

**验收：**过程是“走过去”，不是四宫格上下翻页，也不是原轮播增加 rotateY；不头晕、不黑屏、不丢位置。

### 阶段 3：完整内容与工程化

- 扩展至 11 个活动、50 组展位；处理最后不足四张的情况。
- 完成资源窗口化、派生图、缺图处理、短屏/手机适配和静态降级。
- 保留文档引文出处，完成留言保存、删除、草稿与返回测试。
- 依据完整步道的实走反馈调整留白和长度，再决定是否需要收起的目录/平面入口。
- 将页面上的原型解释性长文移到 README/docs，页面保留必要的留言隐私告知。

**验收：**183 张不漏、不重、不混活动；所有设备能到达最后一站。

### 阶段 4：内部上线

- 与用户确认内部托管位置、可访问人员和身份方式后再发布。
- 仅部署构建产物与获准的展示图，不直接公开整个项目目录、原始图片目录、文档来源文件或旧测试页。
- 如需共享留言，接入服务端身份校验与存储，处理本人删除、输入校验、限流；凭证不放前端。
- 共享存储、身份验证没有完成时，不把本机留言描述成已经多人上线。
- 保留旧版本入口或部署回滚方案。

**交付：**内部可访问地址、真实上线范围说明、验收记录和回滚方法。
